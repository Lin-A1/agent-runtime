# Model Adapter Design

The LLM seam keeps provider-specific behavior behind the existing four-axis `Route`: protocol, endpoint, auth, and framing. `makeLlmClient` remains the compatibility factory for direct `AdapterConfig` values; `extraHeaders` and `maxRetries` are applied at the transport boundary, while `timeout` is metadata for hosts that own cancellation policy.

`packages/llm/src/registry.ts` is both the metadata catalog and executable adapter registry. `ProviderDefinition.createClient(config, fetch?)` is optional: builtins for OpenAI, OpenAI Responses, Anthropic, and OpenAI-compatible deployments delegate to `makeLlmClient`, while metadata-only registrations can describe providers without pretending they are executable. `AdapterRegistry.resolveClient` resolves a provider definition by id (or an `AdapterConfig`'s `providerId`, falling back to its `kind`) and throws `AdapterUnavailableError` for unknown or non-executable providers. `createClient` uses that resolved definition and forwards the injected fetch unchanged, so tests and hosts do not need live network access.

Registry registration remains reversible with duplicate protection and identity-checked disposal. Disposing a registration twice is harmless, and disposal cannot remove a newer value if replacement semantics are added by a host. Registry data is advisory for model/profile capability metadata; it does not override configured routing or secrets. `profileToAdapterConfig` preserves the existing adapter shape for callers that need to turn a selected profile into a client configuration.

Model discovery is metadata-only, not an executable gateway or router. `discoverModels` preserves the `listModels` compatibility signature while exposing status/support details; OpenAI-shaped `data` and compatible `models` lists are accepted, and Anthropic uses its documented `/v1/models` authentication headers without emitting empty API-key headers. Discovery remains fail-soft for manual model entry.

The server exposes the existing read-only `/v1/models` discovery route and `/v1/models/catalog` reference-data route, plus a new redacted `GET /v1/providers` view (active profile pointer, provider profiles with `hasApiKey`/`apiKeyHint`, effective provider kind/baseUrl/model). Catalogs are loaded from the configured agent home and settings responses use runtime redaction; API keys and other secret headers are never part of the public catalog projection. Missing or invalid catalogs fail soft so manual model entry remains available.

Runtime-side resolution lives in `packages/runtime/src/provider-resolution.ts`: `resolveProviderSelection` folds an optional explicit selection (profileId / provider axes / model) over the fully-resolved settings, maps a selected profile to its registry provider id, and throws a typed error for a missing profile instead of silently falling back to a default provider. `AppConfig.adapterRegistry` lets a host inject an executable registry; when present, `createApp` builds its LLM client through `registry.createClient(config.provider)`, otherwise the legacy `makeLlmClient` path applies unchanged. Every durable `Session.ModelCalled` trace now carries `providerId` so usage attribution records the registry identity (explicit profile wins over kind) — the prerequisite for honest failover accounting later.

The registry is intentionally independent of runtime configuration and transport. Hosts can register additional executable providers without changing the turn loop or adding provider branches; custom definitions may implement `createClient` using any compatible protocol/route. The injected-fetch argument keeps the executable seam deterministic and directly integration-testable.
